## 一、为什么要补这份文档

本项目（实时音视频翻译模块）在开工时只做了**技术选型级**对比（whisper 5s 窗口 vs sherpa-onnx 流式；本地 vs 云 API），**没有**做同类产品横向检索。这是流程缺口，已固化为根项目 rules 第 17 条。

## 二、候选方案全景

### 2.1 平台内置能力（第一优先，最容易被忽略）

| 方案 | 形态 | 识别 | 翻译 | 成本 | 关键限制 |
|---|---|---|---|---|---|
| **Chrome 实时字幕 + 实时翻译** | 浏览器内置，无需安装 | 系统/标签页音频 | 送 Google 翻译 | 0 元 | 主要覆盖英文音源；语言支持有限；不可定制 |
| **Chrome 144 Translator API** | 内置 API（Stable） | 不自带 ASR | 端侧翻译 | 0 元 | 只解决翻译，不解决"无字幕轨"的识别 |
| **Edge 实时视频翻译** | 浏览器内置 | 视频音轨 | 字幕 + 配音 | 0 元 | 微软 Q&A 社区答复称该功能当前被标记不可用（**社区信息，待核**） |

**结论**：只求"看外语视频有中文字幕"，Chrome 内置已是零开发成本的答案。本项目必须靠"无字幕轨 + 全本地 + 可定制"立足。

## 三、逐项优缺点分析

### 3.1 sokuji（1484★ / AGPL-3.0）—— 最强竞品

**架构**（读 README + 仓库根目录）：Electron 桌面端 + 浏览器扩展双形态，`sidecar` 子进程 + `model-packs` 模型包 + WASM/WebGPU 端侧推理，ASR → 翻译 → TTS 全链路，支持云端（OpenAI / Gemini / Palabra / Doubao）与本地双模式。

**优点**
- 唯一做到"双向同传 + 语音输出（TTS）+ 虚拟麦克风"的方案，能直接用在 Zoom/Teams/Meet。
- 端侧推理走 WASM/WebGPU，**不依赖 Python 环境**，安装门槛远低于本项目。
- 工程完整度高：CI、发布流水线、THIRD_PARTY_NOTICES、多语言 README、benchmark 目录。

**缺点**
- **AGPL-3.0**：任何衍生作品必须同样开源，商业使用受限。
- 目标是"会议同传"，不是"看视频配字幕"，浮层体验与视频站点适配不是重点。
- 体量大（Electron + 多模型包），冷启动和安装体积明显重于本项目。

**可复用点（仅学设计，不复用代码）**
- `model-packs` 思路：模型按语种打包、按需下载、带校验——本项目现在是 `install_offline_models.py` 粗粒度下载，可借鉴其清单结构。
- 扩展 + 桌面双入口的产品结构，值得在"要不要做独立桌面版"决策时参考。

### 3.2 crx-live-translate（126★ / MIT）—— 架构最近

**架构**：纯浏览器扩展，Web Speech API 做识别，非官方 Google 翻译接口做翻译，结果渲染到页面浮层。

**优点**
- 部署极轻：克隆 → 开发者模式加载即可，**无后端、无模型、无 Python**。
- MIT 许可，代码可自由借鉴。
- 自带**视频全屏按钮**（右下角，5 秒自动隐藏），解决"全屏播放时浮层不可见"这个真实痛点。

**缺点**
- 依赖**虚拟声卡**（Windows Stereo Mix / macOS BlackHole / Linux PAVUCONTROL）才能抓到系统音频，普通用户配置成本高。
- 需要额外装 CORS Unblock 插件绕过跨域，说明其翻译走的是非官方接口，**随时可能失效**。
- 全云依赖，离线不可用；隐私数据出本机。

**可复用点（MIT，可直接借鉴）**
- **全屏浮层方案**：本项目当前浮层在视频全屏时会被遮住，可直接照此思路加一个注入式全屏按钮。
- 设置项实时生效（改设置页即时应用），本项目的弹窗选语种可参考其交互。

### 3.3 kami-subs（8★ / MIT）—— 与本项目最像

**架构**（README 原文）：`Chrome tabCapture → PCM 16k 单声道 → WebSocket → Python 后端 faster-whisper → 翻译 → JSON 回传 → 页面浮层`，后端跑 `FastAPI WS @ :8765`。

**优点**
- 链路与本项目**几乎同构**（tabCapture + WS + 本地 ASR + 浮层），是最直接的对标物。
- **Native Messaging 让扩展自己拉起后端**——点 Start 就自动起 Python 进程，用户不用开终端。这是本项目目前最缺的体验（现在要手动双击 `启动.bat`）。
- README 把"为什么要有这个东西"写得很清楚，直接点明 Chrome 内置 Live Caption 只支持英文且不翻译。

**缺点**
- 仅 Windows；强依赖 NVIDIA GPU + CUDA，CPU 下 3-5s 延迟。
- 用 faster-whisper 的**窗口式**识别（非流式），本质上就是本项目早期被淘汰的方案（5s 窗口延迟）。
- star 极少（8），工程成熟度低，缺少测试与回归。

**可复用点（MIT，可直接借鉴）**
- **Native Messaging 自动拉起后端**：可显著降低本项目使用门槛，优先考虑。
- 模型档位建议表（tiny/base/small/large-v3-turbo 对应延迟与显存），可直接补进本项目 README。

### 3.4 youtube-subtitle-translator（41★ / MIT）—— 只读字幕轨

**优点**：不做 ASR，直接读平台已有字幕轨再翻译，**零延迟、零算力**，在有 CC 的视频上体验碾压所有 ASR 方案。
**缺点**：无字幕轨就完全失效——这正是本项目的生存空间。
**可复用点**：**字幕轨优先策略**——先探测页面是否已有 CC 轨，有则直接读、没有才启用音频识别。本项目目前一律走音频识别，白白浪费了"有轨视频"这条捷径。

## 四、本项目（实时音视频翻译模块）定位

### 4.1 差异化立足点

组合起来的稀缺性，不在任何单点：

1. **无字幕轨也能出中文**——不依赖平台 CC，任何视频/直播音频都能处理（`youtube-subtitle-translator` 做不到）。
2. **端侧流式 ASR**——sherpa-onnx streaming zipformer，不是 5s 窗口（`kami-subs` 做不到）。
3. **本地 CT2 翻译，0 元 0 云**——无 API Key、无按分钟计费、音频不出本机（`crx-live-translate` 做不到）。
4. **中日韩英 + 中文母语优化**——目标用户是中文观众，而非英文会议。

### 4.2 明确劣势（必须承认）

| 维度 | 本项目 | 对手 |
|---|---|---|
| Star / 社区 | 0（未开源） | sokuji 1484 |
| 安装门槛 | 需 Python 3.13 + 手动启动后端 + 下载模型 | sokuji 装包即用；crx-live-translate 拖进去就行 |
| 延迟 | 端到端 1.66–2.54s，**未达 ≤1s** | kami-subs GPU 下宣称亚秒 |
| 功能广度 | 只做字幕，无 TTS、无双向 | sokuji 有 TTS + 虚拟麦克风 |
| 平台 | 仅 Windows | sokuji 全平台 |

### 4.3 结论

**不是重复造轮子，但也不是最优解**：
- 若需求只是"看英文视频要中文字幕"→ 用 Chrome 内置，本项目没有存在价值。
- 若要"任意音源 + 全本地 + 0 成本 + 中文优先"→ 本项目的最优组合目前没有等价开源实现。
