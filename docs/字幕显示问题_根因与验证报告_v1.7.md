## 一、问题现象

| 现象 | 用户侧表现 |
|---|---|
| 日文字幕完全不出现 | 播放日语视频，扩展浮层无字幕或只有拉丁字母乱码 |
| 日文字幕文件加载后乱码/缺字 | 加载 `.srt/.vtt/.ass` 后出现 `??????`、波浪线变成方块、假名不显示 |
| 越用越不出字幕 | 连续切换多个视频/标签页后，字幕延迟从 1-2s 涨到 10-30s，最终 0 条 |
| 中文字幕偶发消失 | 多连接并存时后续连接收不到任何字幕 |

## 二、根因清单（按链路：音频→ASR→翻译→字幕文件→渲染）

### R1　ASR 模型语种缺失（最致命）

- **事实**：流式模型 `sherpa-onnx-streaming-zipformer-small-bilingual-zh-en-2023-02-16` 只覆盖中/英。日语音频被强行解码成拉丁字母，实测输出 `CURIKARA KO AND YAKIMAS`（「今日はとても良い天気です」）。
- **修复**：新增 `LangRoutePipeline`（`server/browser_audio.py`）——先攒 `SNIFF_SEC=2.0s` 音频用 whisper 判语种（`language=None` + 读 `info.language/language_probability`），zh/en 且置信度 ≥0.5 才走流式，其余（ja/ko/低置信）走 `BrowserAudioPipeline`（faster-whisper tiny int8，四语通用）。判定完成后把已缓存音频整段补喂给后端，不丢内容。`LIVESUB_LANG`/`?lang=` 可显式指定跳过嗅探。
- **实测**：路由日志 `[asr] 语种路由（自动嗅探）lang=ja prob=0.99 → whisper`；日语原文完整输出 `今日はとても良い天気です`。

### R2　日/韩碎片译文退化（星号/问号乱码）

- **事实**：本地 CT2 对短碎片（如「これから声」）日→英→中两跳时，输出 `⁇⁇⁇` 之类退化串，前端表现为乱码。
- **修复**：`offline_translate/engines.py` 新增 `DegenerateError(EngineError)` 与 `is_degenerate()`（非空白字符中 `⁇?？*＊` 占比 ≥0.2 判退化）；`Translator.translate` 检出后立即停止换引擎，返回 `{"failed":True,"degenerate":True,"translated":原文}`，宁可回显原文也不吐乱码。实测 `'これから声'` 0.02s 内直接回退原文。
- **回归断言**：ws 测试每语种均有「无星号/问号退化解」检查，实测全部 `[]`。

### R3　冷启动把首条字幕拖到断连之后

- **事实**：whisper tiny 首次 `transcribe` 12.3s、`Translator` 冷启动 10.2s（含 82MB 本地模型），首个连接的首条字幕被推后到十几秒。
- **修复**：`server/main.py::_warm_pipelines()` 启动即加载 `get_model()` / `get_translator()`，并跑一次 **哑推理** `detect_language(np.zeros(16000))` 把计算图热起来（只加载权重不够）。
- **实测**：日志 `[warmup] whisper 语种嗅探 + 多语种通道就绪（首判预热 1987ms）`（同一命令另一次受机器负载影响为 9142ms，均远低于原 12.3s 的冷启动叠加）。

### R4　Whisper 单例被多线程并发调用 → 全局劣化「越用越慢」

- **事实**：whisper 是进程内单例，语种嗅探与各连接的窗口识别分属不同线程；并发 `transcribe` 会把 6 个 ctranslate2 线程打满（4 核机器超订）。实测第 3 轮连接后单条 `latency_ms=36798`（`mt_ms=33709`）。
- **修复**：模块级 `_infer_lock` 串行化所有 whisper 推理（`detect_language` 与窗口识别共用）。

### R5　嗅探期间断连 → 僵尸管道叠加

- **事实**：客户端在语种判定完成前断开时，`_decide()` 仍照常创建后端，新管道拿不到 `stop()`，成为永远空转的线程（日志中多套 `[dbg] idle#N ... stop=False` 并行增长）。
- **修复**：`_decide()` 开头判 `self._stop.is_set()` 直接放弃创建；`_worker` 在取到窗口后再判一次 `_stop` 并退出。

### R6　跨连接嗅探饥饿 → 新连接 0 字幕

- **事实**（本轮新发现）：`_infer_lock` 串行化后，第 4 个连接的语种嗅探被前序连接仍在排队的窗口识别挤在后面，`[asr] 语种路由` 晚于 `[ws/audio] 客户端断开，已收 46 块`，触发 R5 的拦截 → 该连接 0 字幕（首轮回归 `PASS 88 / FAIL 2`，韩/英 0 条）。
- **修复**：嗅探提升为高优先级——`detect_language` 登记 `_sniff_waiting` 后直接抢锁；窗口识别改走 `_acquire_window_infer()`（低优先级），发现 `_sniff_waiting > 0` 时在锁外每 50ms 让路。
- **实测**：连续两轮 15/15；两轮日志共 8 个连接，**全部**为「路由 → 断开」顺序，无 `连接已关闭，放弃创建后端`，无异常堆栈。

### R7　字幕文件编码误判（cp932 vs JIS X 0213）

- **事实**：Shift_JIS 的 `～`(U+FF5E) 与 JIS X 0213 的 `〜`(U+301C) 同字节序列不同码位；`charset_normalizer` 把 cp932 文件识别成 `shift_jis_2004`，导致波浪线被映射成另一个字符（与原文逐字比对失败）。
- **修复**：`server/subtitle_file.py` 增加 `_ENC_NORMALIZE`（`shift_jis_2004/shift_jisx0213 → cp932`、`euc_jis_2004/euc_jisx0213 → euc_jp`），先归一再插候选；解析失败按 charset_normalizer → 候选编码打分兜底，统一转 UTF-8 JSON 返回。

### R8　渲染层缺日文字体 fallback

- **事实**：本机字体实测（canvas 宽度度量，同字号同文本）：Meiryo **317.24px == 不存在字体的测量值**（说明未安装），Yu Gothic 319.99px，MS Gothic 333.5px。可用：`YuGothR.ttc`、`msgothic.ttc`、`NotoSansSC-VF.ttf`；**无 Meiryo**。原样式只写通用 sans-serif，日文假名/特殊符号可能落到缺字字体。
- **修复**：`web/index.html` 中 `#subs.lang-ja` / `#fileSubs.lang-ja` 使用字体栈
  `"Yu Gothic","Hiragino Kaku Gothic ProN","Meiryo","MS Gothic","Noto Sans CJK JP","Microsoft YaHei","PingFang SC",sans-serif`；
  `lang-ko` 使用 `"Malgun Gothic","Yu Gothic","Microsoft YaHei"`。字体按栈顺序逐级回退，未装 Meiryo 时自动落到 Yu Gothic / MS Gothic。

## 五、遗留与限制（如实标注）

1. **日/韩首条字幕 2.7-8.1s**：whisper 通道本质是非流式（2.5s 窗口 / 1.5s 步进），CPU 上无法做到中英那样的 200-500ms。要提速需另装 ja/ko 流式模型（当前未装）。✅ **11-10 已解决**：ja/ko 流式模型已装并接入，显式 `?lang=` 首条 198-775ms（见 README）。
2. **浏览器端到端延迟仍缺一次真实点击实测**：需在真实 Chrome 点一次扩展图标并播放 ≥10s。未取得前不得对外声称端到端 ≤1s（服务端链路 p50 200-350ms 已有实测）。
3. **本机无 Meiryo**：字体栈已按实测可用字体排序（Yu Gothic → MS Gothic → Noto Sans CJK JP），其他机器上若装了 Meiryo 仍会优先使用更靠前的 Yu Gothic。
4. **whisper 通道在 4 核机器上与流式 ASR/翻译争核**：已用 `_infer_lock` 串行化避免劣化，但吞吐上限受硬件约束；多标签页同时跑日/韩会排队。
5. 日语音同音字（如「午後は」→「ごごは」）与纯汉字无假名句被判成中文属 ASR/语种判定固有取舍，非本次缺陷。
